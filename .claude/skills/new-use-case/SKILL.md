# new-use-case

Scaffolds the documentation artifacts for a new use case in this repo, per the doc-first
workflow: a requirement should already exist (or be added first) in
`docs/requirements/functional.md` or `non-functional.md` before running this.

## Input

`args` is a short use case name, e.g. "update note" or "search notes by tag".

## Steps

1. Find the next free use case number by listing `docs/usecases/uc-*.md` and incrementing
   the highest `NN` found (start at `01` if none exist).
2. Slugify the input (lowercase, hyphens) to build `uc-NN-<slug>.md` and
   `uc-NN-<slug>.puml`.
3. Ask the user (if not obvious from context) which FR/NFR id(s) this use case satisfies.
   There is one driving adapter in this project (REST) — no need to ask which adapter it's
   reachable from.
4. Write `docs/usecases/uc-NN-<slug>.md` using this template:

   - **ID / Name**
   - **Primary Actor**
   - **Trigger**
   - **Preconditions**
   - **Main Success Scenario** — numbered steps, each naming the layer/adapter that
     handles it (driving adapter → application use case → domain → port → driven adapter)
   - **Extensions / Exceptions**
   - **Postconditions**
   - **Related FR/NFR**

5. Write `docs/usecases/uc-NN-<slug>.puml` — a sequence diagram showing the REST entry
   point, the application use-case call, then one path down through domain → port →
   driven adapter. If the use case spans more than one HTTP request (e.g. an OAuth
   redirect's start/callback legs, see `uc-03-login-with-oauth-provider.puml`), show both
   legs in sequence with an `alt` block only around genuine branching (state mismatch,
   exchange failure), not around adapter choice — there's only one driving adapter here.
   Match the style of `docs/usecases/uc-01-register-with-password.puml`, including its
   `!include ../architecture/_style.puml` line near the top, so all use-case diagrams
   share one set of skinparams.

   Tag the arrow that fulfills each Main Success Scenario step with a `[UC-NN.n]` prefix
   on the message label (e.g. `REST -> UseCase : [UC-01.1-2] CreateNoteInput`), so a step
   can be pointed at directly in the diagram while troubleshooting:
   - When a step is a pure receipt with no distinct message of its own (e.g. "application
     receives the DTO" happens the instant the prior call arrives), fold it into the
     producing message's tag as a range: `[UC-NN.1-2]`.
   - Tag branches from `Extensions / Exceptions` with their letter suffix, on the arrow(s)
     in the corresponding `alt` error branch (e.g. `[UC-01.3a]`).
   - Add a closing `note over <first>, <last>` pointing back at the `.md` file, e.g.
     `[UC-NN.n] tags map to Main Success Scenario step n in uc-NN-<slug>.md`.

   In the `.md` file, add one line under the `## Main Success Scenario` heading: `Each
   step is tagged [UC-NN.n] on its corresponding message in uc-NN-<slug>.puml.`
6. Append a row to `docs/v-model/traceability.md`: Requirement | this UC | `planned` for
   the three test columns.
7. Add this use case's oval to `docs/architecture/use-case-diagram.puml`, connected to the
   existing actor, following the pattern of the ovals already there.
8. Report the files created and remind the user this is documentation only — no code is
   generated by this skill.
